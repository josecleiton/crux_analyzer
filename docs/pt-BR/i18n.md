# Internacionalização

> 🌐 [English](../i18n.md) · **Português (Brasil)**

O crux_analyzer fala **inglês** (`en`) e **português do Brasil** (`pt-BR`) nas
três superfícies em que produz texto: a UI web, a CLI e a documentação gerada.

O inglês é o **locale de origem**. As chaves são escritas em inglês, o inglês é o
fallback quando a resolução falha, e uma tradução ausente degrada para inglês em
vez de virar um rótulo vazio.

## A linha divisória: prosa vs. dados

A maioria das strings nesta base de código *não* é traduzível, e inverter isso é a
principal forma de quebrar a ferramenta:

| Traduzir | Nunca traduzir |
| --- | --- |
| Rótulos, títulos, botões, estados vazios, diagnósticos, cabeçalhos de tabela | Nomes de core, máquina, estado, evento e efeito — são identificadores Rust lidos da aplicação analisada |
| Prosa que substitui um sentinela (`"*"` → "qualquer estado") | O sentinela em si (`State::ANY`, `ANY_STATE_NAME`) |
| O *rótulo de exibição* do pseudo-estado Mermaid | O **id** do nó `any_state` — as linhas de transição se referem a ele, então é sintaxe |
| Mensagens de status e erro da CLI | Valores de `--format` (`markdown`/`mermaid`), chaves de opção do ELK, texto de `throw`/`console.warn` só para desenvolvedores |
| Nosso rótulo para um marcador (`failure` → "failure" / "falha") | O **valor** do marcador no modelo (`failure`, `deprecated`) e os nomes de `@tag` do autor — ambos estão escritos na fonte analisada |

### A terceira categoria: a prosa do autor

Comentários de documentação lidos da fonte analisada (`///` em um enum de estado
ou em suas variantes) são uma terceira categoria: **prosa que é dado**. O
crux_analyzer os copia literalmente para `machines[].doc` e `states[].doc` e nunca
os traduz, exatamente como copia o nome de um estado — a língua desse texto é
escolha do autor, não nossa. A independência de locale continua valendo:
`crux-analyzer generate` ainda produz JSON byte a byte idêntico em todo locale,
porque o locale nunca chega até a cópia. O que *é* localizado é apenas o nosso
enquadramento desse dado — os cabeçalhos de coluna `Estado` / `Descrição` /
`Marcadores` / `Etiquetas` e os nomes humanos dos marcadores.

É aqui também que a regra de honestidade do parser se encaixa. `@failure` não é o
parser adivinhando que um estado significa falha; é o parser lendo o que o autor
declarou — dado, como o nome de um estado. O *palpite* (um estado chamado `Failed`
provavelmente é uma falha) continua onde sempre esteve, na UI
(`domain/stateRole.ts`).

A UI web te dá uma regra visual de graça: **monoespaçado é dado**, sem serifa é
interface (`src/index.css`).

O **modelo JSON é independente de locale** por contrato. Tudo nele é lido da fonte
analisada — identificadores e, desde que os comentários de documentação chegaram
ao modelo, a prosa do próprio autor — então `crux-analyzer generate` produz saída
byte a byte idêntica em todo locale e nenhum texto **do próprio crux_analyzer**
jamais entra no schema. A prosa do autor é copiada literalmente, nunca traduzida.
Veja [schema.md](schema.md) e a terceira categoria acima.

## Onde vivem os catálogos

Não existe um arquivo central de traduções. Cada crate é dono do catálogo das
strings que emite, o que mantém o grafo de dependências como um funil limpo e faz
com que nenhum crate precise conhecer o conjunto de mensagens de outro:

| Superfície | Catálogo |
| --- | --- |
| O tipo `Locale` + detecção | `crates/i18n` — **apenas** o tipo, sem mensagens |
| Diagnósticos do parser | `crates/parser/src/i18n.rs`, indexados por `WarningKind` / `ParseError` |
| Documentos gerados | `crates/docgen/src/labels.rs` (`Labels::EN`, `Labels::PT_BR`) |
| Saída da CLI em tempo de execução | `crates/cli/src/i18n.rs` |
| UI web | `apps/web/src/i18n/messages/{en,pt-BR}.ts` |

### Glossário

Os rótulos de prosa que os geradores e a UI compartilham, para que ambas as
superfícies se leiam do mesmo jeito:

| en | pt-BR |
| --- | --- |
| Core | Núcleo |
| Machine | Máquina |
| From / Event / To / Effects | De / Evento / Para / Efeitos |
| States / State / Description | Estados / Estado / Descrição |
| Markers / Tags | Marcadores / Etiquetas |
| failure / deprecated (rótulos de marcador) | falha / descontinuado |
| any state | qualquer estado |
| Inspector | Inspetor |
| Simulation | Simulação |

## Lado Rust

`crux_analyzer_i18n::Locale` é o tipo compartilhado. `Locale::from_env()` o
resolve a partir de `CRUX_ANALYZER_LOCALE`, depois da cadeia POSIX `LC_ALL` →
`LC_MESSAGES` → `LANG` (interpretando `pt_BR.UTF-8`), caindo para `en`. Valores de
*ambiente* não reconhecidos caem em silêncio; um `--locale` explícito não
reconhecido é erro, porque ignorar o que o usuário pediu seria pior.

Diagnósticos são construídos como **dados** e renderizados como prosa somente
quando exibidos:

```rust
Warning { file, line, kind: WarningKind::DynamicTarget { machine } }
warning.render(locale)   // `arquivo:linha: mensagem` localizado
warning.to_string()      // inglês — Display é o locale de origem
```

`WarningKind::code()` devolve um identificador estável e independente de locale
(`dynamic-target`, ...). **Baseie documentação e ferramentas no código, nunca na
prosa** — veja a [referência de avisos](parser.md#referência-de-avisos).

Os geradores recebem o locale explicitamente: `markdown(&project, locale)` e
`mermaid_diagrams(&project, locale)` o resolvem em um `Labels` uma única vez.

## Lado web

`apps/web/src/i18n/` espelha `src/theme/` de propósito: mesma ordem de resolução
(escolha explícita → preferência do navegador), mesmo tratamento de
"armazenamento pode estar desabilitado", mesmo bootstrap pré-pintura em
`index.html`.

- `locale.ts` — o contrato: `Locale`, `LOCALE_STORAGE_KEY`, `storedLocale`,
  `systemLocale` (a partir de `navigator.languages`; qualquer português resolve
  para `pt-BR`), `currentLocale`, `applyLocale`. Define `data-locale` **e** `lang`
  no `<html>`.
- `translate.ts` — busca livre de DOM, interpolação `{nome}` e um helper
  `plural()` sobre `Intl.PluralRules`. Mantido livre de DOM para ser testável no
  ambiente de teste `node` padrão do projeto.
- `context.ts` / `I18nProvider.tsx` / `useI18n.ts` — o contexto, o provider
  (montado em `main.tsx`) e os hooks `useI18n()` / `useTranslate()`. São três
  arquivos porque um módulo que exporta ao mesmo tempo um componente e hooks
  quebra o React Fast Refresh.

A única divergência deliberada em relação ao tema: o tema passa por props porque
dois componentes precisam dele, enquanto `t` é necessário em todo painel, então
ele vem por **contexto**.

`messages/en.ts` define o conjunto de chaves e exporta o tipo `Catalog`;
`messages/pt-BR.ts` é anotado com ele, então **o `tsc` é a verificação de
paridade** — uma chave ausente ou escrita errada quebra `just web-build`. Um teste
em tempo de execução em `translate.test.ts` afirma o mesmo para quem rodar apenas
os testes.

### Regras ao adicionar texto de interface

1. Nenhum literal visível ao usuário inline em um componente — adicione uma chave.
2. Adicione primeiro em `en.ts`; o `tsc` então vai exigir todos os outros
   catálogos.
3. Prefira **uma chave por frase completa** a templates que interpolam uma palavra
   traduzida. `Switch to {mode}` quebra em idiomas que flexionam o adjetivo;
   `themeToggle.switchToLight` / `switchToDark` não. Interpolação é para dados
   (nomes, contagens), não para vocabulário.
4. Strings com contagem usam `plural()`, nunca `"1 estado(s)"` ou
   `n + ' estados'`.
5. Texto traduzido é **apresentação**: ele é injetado em `flow/` (veja
   `FlowLabels`) em vez de importado lá. As larguras dos nós são estimadas a
   partir do rótulo, então a string *traduzida* é a que precisa ser medida — é por
   isso que trocar de locale refaz o layout em vez de apenas re-renderizar.

## Lacuna conhecida: `--help` só em inglês

`crux-analyzer --help` permanece em inglês. A API de derive do clap tira o texto
de ajuda de comentários de documentação, que são `'static` e resolvidos antes de
`--locale` poder ser lido; localizá-los significa abandonar a macro de derive pela
API de builder. Esse custo foi julgado não valer a pena — toda a saída de *tempo
de execução* é localizada. A linha `about` de nível superior vem da `description`
em `crates/cli/Cargo.toml`, que tem a mesma restrição.

## Adicionando um locale

1. `crates/i18n`: adicione a variante, seu `tag()`, `endonym()` e o braço do match
   em `from_tag`; estenda `Locale::ALL`.
2. Adicione um braço a cada catálogo Rust listado acima — a verificação de
   exaustividade do compilador vai apontar para todos eles.
3. `apps/web/src/i18n`: adicione `messages/<tag>.ts` tipado como `Catalog`,
   registre-o em `translate.ts` e estenda `LOCALES`, `localeEndonym`,
   `localeShortLabel` mais o script pré-pintura em `index.html`.
4. Adicione uma invocação de `example-docs-locale` no `Justfile` e traduza o
   conjunto de documentos em `docs/<tag>/`.

Note que o alternador da barra de ferramentas circula por `LOCALES`; passando de
dois locales, ele deve se tornar um menu.

## Documentação

O conjunto de documentos em inglês é a fonte; [`docs/pt-BR/`](README.md) o
espelha. `docs/pt-BR/examples/mini-recorder.md` é **gerado**, não traduzido à mão
— `just example-docs` atualiza todos os locales.

Aquele arquivo contém frases em inglês sob cabeçalhos de tabela em português: são
os próprios comentários de documentação da fixture, copiados literalmente. Isso é
a regra da terceira categoria funcionando, não uma tradução faltando.

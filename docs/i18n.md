# Internationalization

> 🌐 **English** · [Português (Brasil)](pt-BR/i18n.md)

crux_analyzer speaks **English** (`en`) and **Brazilian Portuguese**
(`pt-BR`) across all three surfaces it produces text on: the web UI, the CLI,
and generated documentation.

English is the **source locale**. Keys are authored in English, English is the
fallback whenever resolution fails, and a missing translation degrades to
English rather than to a blank label.

## The dividing line: prose vs. data

Most strings in this codebase are *not* translatable, and getting this
backwards is the main way to break the tool:

| Translate | Never translate |
| --- | --- |
| Labels, headings, buttons, empty states, diagnostics, table headers | Core, machine, state, event and effect names — they are Rust identifiers read out of the analyzed application |
| Prose standing in for a sentinel (`"*"` → "any state") | The sentinel itself (`State::ANY`, `ANY_STATE_NAME`) |
| The Mermaid pseudo-state's *display label* | Its node **id** `any_state` — transition lines refer to it, so it is syntax |
| CLI status and error messages | `--format` values (`markdown`/`mermaid`), ELK option keys, developer-only `throw`/`console.warn` text |
| Our label for a marker (`failure` → "failure" / "falha") | The marker **value** in the model (`failure`, `deprecated`), and the author's `@tag` names — both are written in the analyzed source |

### The third category: author prose

Doc comments read off the analyzed source (`///` on a state enum or its
variants) are a third category: **prose that is data**. crux_analyzer copies it
verbatim into `machines[].doc` and `states[].doc` and never translates it,
exactly as it copies a state name — the language of that text is the author's
choice, not ours. Locale-independence is unaffected: `crux-analyzer generate`
still produces byte-identical JSON in every locale, because the locale never
reaches the copy. What *is* localized is only our framing of that data — the
`State` / `Description` / `Markers` / `Tags` column headers, and the human names
of the markers.

This is also where the parser honesty rule lands. `@failure` is not the parser
guessing that a state means failure; it is the parser reading what the author
declared — data, like a state name. The *guess* (a state named `Failed` is
probably a failure) stays where it always was, in the UI
(`domain/stateRole.ts`).

The web UI gives you a visual rule for free: **monospace is data**, sans-serif
is chrome (`src/index.css`).

The **model JSON is locale-independent** by contract. Everything in it is read
out of the analyzed source — identifiers, and since doc comments reached the
model, the author's own prose — so `crux-analyzer generate` produces
byte-identical output in every locale and no text **of crux_analyzer's own** ever
enters the schema. Author prose is copied verbatim, never translated. See
[schema.md](schema.md) and the third category below.

## Where the catalogs live

There is no central translation file. Each crate owns the catalog for the
strings it emits, which keeps the dependency graph a clean fan-in and means no
crate has to know another's message set:

| Surface | Catalog |
| --- | --- |
| The `Locale` type + detection | `crates/i18n` — **only** the type, no messages |
| Parser diagnostics | `crates/parser/src/i18n.rs`, keyed off `WarningKind` / `ParseError` |
| Generated documents | `crates/docgen/src/labels.rs` (`Labels::EN`, `Labels::PT_BR`) |
| CLI runtime output | `crates/cli/src/i18n.rs` |
| Web UI | `apps/web/src/i18n/messages/{en,pt-BR}.ts` |
| VS Code extension chrome | `apps/vscode/package.nls*.json` (contribution points) + `apps/vscode/l10n/` (runtime, via `vscode.l10n`) |

The extension's *panel content* is the web bundle, so it follows the web UI's
catalogs and locale toggle; only the extension's own chrome (command title,
settings, error messages) uses the VS Code mechanisms.

## Rust side

`crux_analyzer_i18n::Locale` is the shared type. `Locale::from_env()` resolves
it from `CRUX_ANALYZER_LOCALE`, then the POSIX chain `LC_ALL` → `LC_MESSAGES` →
`LANG` (parsing `pt_BR.UTF-8`), falling back to `en`. Unrecognized *environment*
values fall back silently; an unrecognized explicit `--locale` is an error,
because ignoring what the user asked for would be worse.

Diagnostics are constructed as **data** and rendered as prose only when shown:

```rust
Warning { file, line, kind: WarningKind::DynamicTarget { machine } }
warning.render(locale)   // localized `file:line: message`
warning.to_string()      // English — Display is the source locale
```

`WarningKind::code()` returns a stable, locale-independent identifier
(`dynamic-target`, ...). **Key documentation and tooling on the code, never on
the prose** — see the [warnings reference](parser.md#warnings-reference).

Generators take the locale explicitly: `markdown(&project, locale)` and
`mermaid_diagrams(&project, locale)` resolve it into a `Labels` once.

## Web side

`apps/web/src/i18n/` deliberately mirrors `src/theme/`: same resolution order
(explicit choice → browser preference), same "storage may be disabled"
handling, same pre-paint bootstrap in `index.html`.

- `locale.ts` — the contract: `Locale`, `LOCALE_STORAGE_KEY`, `storedLocale`,
  `systemLocale` (from `navigator.languages`; any Portuguese maps to `pt-BR`),
  `currentLocale`, `applyLocale`. Sets `data-locale` **and** `lang` on `<html>`.
- `translate.ts` — DOM-free lookup, `{name}` interpolation, and a `plural()`
  helper over `Intl.PluralRules`. Kept DOM-free so it is testable in the
  project's default `node` test environment.
- `context.ts` / `I18nProvider.tsx` / `useI18n.ts` — the context, the provider
  (mounted in `main.tsx`), and the `useI18n()` / `useTranslate()` hooks. They
  are three files because a module that exports both a component and hooks
  breaks React Fast Refresh.

The one deliberate divergence from the theme: the theme threads through props
because two components need it, while `t` is needed by every panel, so it comes
through **context**.

`messages/en.ts` defines the key set and exports the `Catalog` type;
`messages/pt-BR.ts` is annotated with it, so **`tsc` is the parity check** — a
missing or misspelled key fails `just web-build`. A runtime test in
`translate.test.ts` asserts the same thing for anyone running tests alone.

### Rules when adding UI text

1. No user-facing literal inline in a component — add a key.
2. Add it to `en.ts` first; `tsc` will then demand every other catalog.
3. Prefer **one key per complete phrase** over templates that interpolate a
   translated word. `Switch to {mode}` breaks in languages that inflect the
   adjective; `themeToggle.switchToLight` / `switchToDark` does not.
   Interpolation is for data (names, counts), not for vocabulary.
4. Counted strings use `plural()`, never `"1 state(s)"` or `n + ' states'`.
5. Translated text is **presentation**: it is injected into `flow/` (see
   `FlowLabels`) rather than imported there. Node widths are estimated from the
   label, so the *translated* string is the one that must be measured — this is
   why switching locale re-runs layout instead of only re-rendering.

## Known gap: `--help` is English-only

`crux-analyzer --help` stays in English. clap's derive API takes help text from
doc comments, which are `'static` and resolved before `--locale` can be read;
localizing them means dropping the derive macro for the builder API. That cost
was judged not worth it — all *runtime* output localizes. The top-level `about`
line comes from `crates/cli/Cargo.toml`'s `description`, which has the same
constraint.

## Adding a locale

1. `crates/i18n`: add the variant, its `tag()`, `endonym()`, and the
   `from_tag` match arm; extend `Locale::ALL`.
2. Add an arm to each Rust catalog listed above — the compiler's exhaustiveness
   checking will point at every one of them.
3. `apps/web/src/i18n`: add `messages/<tag>.ts` typed as `Catalog`, register it
   in `translate.ts`, and extend `LOCALES`, `localeEndonym`,
   `localeShortLabel` plus the pre-paint script in `index.html`.
4. Add an `example-docs-locale` invocation in the `Justfile` and translate the
   doc set under `docs/<tag>/`.

Note the toolbar switcher cycles through `LOCALES`; past two locales it should
become a menu.

## Documentation

The English doc set is the source; [`docs/pt-BR/`](pt-BR/README.md) mirrors it.
`docs/pt-BR/examples/mini-recorder.md` is **generated**, not translated by hand
— `just example-docs` refreshes every locale.

That file contains English sentences under Portuguese table headers: they are
the fixture's own doc comments, copied verbatim. That is the third-category rule
working, not a missing translation.
